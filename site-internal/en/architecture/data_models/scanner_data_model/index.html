    Data Model: RTMS Scanner¶

    This document describes the database tables utilized by rtms-scanner and its management backend (rtms-commons), organized across schemas admin and scanner.

    Schema admin¶

    This schema manages global context, multi-tenancy, CVE alerts, consolidated inventory, and platform administration.

    Table Description
    admin.tenant_infra Master multi-tenancy table. Identifies each client tenant to isolate data, alerts, and configurations.
    admin.assets Consolidated global inventory of all discovered network devices and hosts associated with a tenant.
    admin.asset_software List of software packages, applications, and operating systems detected on each asset.
    admin.asset_vulnerabilities Mappings between discovered assets and identified vulnerabilities (CVEs).
    admin.cve_alerts Audit history and logging of triggered and dispatched security alerts.
    admin.cve_alerts_config Alerting rule configuration per tenant (e.g., severity threshold, notification channels such as email or webhook).
    admin.login_audit Audit log tracking user logins, sessions, and platform administrative actions.
    admin.nvd_config NVD integration parameters and API keys for CVE synchronization per tenant.
    admin.product_license RTMS license management (validity expiration, licensed feature set).
    admin.service_registry Registration and heartbeat monitoring for RTMS microservices (scanners, agents, NVD). Stores local scanner configuration: subnets, deep scan, exclusions, Wi-Fi scans (scan_wifi), Ethernet scans (scan_ethernet), and SNMP options (snmp_scan, snmp_target_ip, snmp_community).
    admin.subnet_names Custom labels and descriptions assigned to CIDR subnets (e.g., DMZ, Production, Guest Wi-Fi) managed via the web portal.
    admin.subnet_mac_whitelist Allowed MAC address whitelist per CIDR subnet, suppressing alerts for legitimate recurring devices (NEW_HOST and unknown device warnings).
    admin.system_config Global platform system settings, including master hardware switches: Wi-Fi scanning (wifi_scan_enabled) and Ethernet scanning (ethernet_scan_enabled).
    admin.tenant_assets Table managing lifecycle and tenant-specific asset relationships.
    admin.tenant_asset_software Table managing lifecycle and tenant-specific software packages.
    admin.users User accounts authorized to access the RTMS web administration portal.
    admin.vulnerability_view (SQL View) Aggregation view simplifying queries for vulnerability dashboard reporting.

    Schema scanner¶

    This schema is dedicated to the technical probing engine. It stores scan configurations, execution histories, and raw discovery results.

    Table Description
    scanner.organizations Logical groupings (e.g., physical site, office, datacenter) segmenting network scanning boundaries.
    scanner.networks CIDR subnets monitored and scanned by the probe engine for a given organization.
    scanner.network_mappings Gateway and routing mappings (e.g., network to gateway MAC address) used to detect topology changes and spoofing.
    scanner.excluded_ips Explicit list of IP addresses or ranges to skip during scan cycles.
    scanner.scanner_config Dynamic key-value configuration store for the scanner (intervals, Nmap flags, execution switches, and synchronization of scanner.global_wifi_scan_enabled / scanner.global_ethernet_scan_enabled).
    scanner.scans Scan execution history (start/end timestamps, status, raw JSON dump).
    scanner.scan_archives Complete network scan snapshots (JSONB archive consolidating hosts, ports, services, and software with automated diff calculation and export).
    scanner.services Inventory of discovered open ports and network services.
    scanner.vulnerabilities Vulnerabilities detected directly via active network probes (e.g., Nmap NSE scripts).
    scanner.alerts Operational alerts generated by the scanner (new device, IP change, gateway ARP spoofing, MAC conflict).
    scanner.host_tags Custom tags assigned to discovered hosts for search and categorization.
    scanner.itop_assets Synchronization and mapping table for external CMDBs such as Combodo iTop.

    Subnet Operational State & Lifecycle¶

    The system continuously evaluates the operational state of each subnet across three complementary tiers:

    1. Tier 1: Physical Interface Presence ("Disconnected")
    2. The scanning engine polls local network interfaces at startup and on every heartbeat (check_env()).
    3. CIDR blocks assigned to active physical interfaces are stored in the subnet column of admin.service_registry.
    4. If an inventory subnet matches no active local physical interface, the probe cannot emit Layer 2 ARP frames.

    5. The subnet is marked Disconnected (isSubnetConnected = false, subnet_active = false), its hosts are shown offline, and its web inventory display is automatically collapsed into a single row.

    6. Tier 2: Host Discovery & Reachability ("Inactive / Offline")

    7. If the scanner has an active interface on the subnet (isSubnetConnected = true), it runs periodic sweeps (ARP, ICMP ping, Nmap).
    8. If at least one host responds, the subnet is Online (Green) (isSubnetOnline = true).
    9. If the scan executes but no host responds (all known devices are powered off or unreachable), the online host counter drops to 0.

    10. The subnet is marked Inactive / Offline (isSubnetOnline = false) and is also collapsed into a single row in the web interface.

    11. Tier 3: Scanner Mobility & Roaming

    12. When a mobile host (e.g., laptop running rtms-scanner) moves from Subnet A to Subnet B:
      • Service Registry (admin.service_registry): The scanner record (keyed by hardware machine_id) is updated in-place (new subnet, new host_ip, status reset to RUNNING). Stale duplicate records with the same machine_id are purged.
      • Subnet Preservation: Subnet A is not deleted from scanner.networks; it simply transitions to "Disconnected" status and remains readable.
      • Asset Preservation: Assets discovered on Subnet A remain intact in admin.assets with their historical last_seen timestamp. Scanning Subnet B does not overwrite or corrupt Subnet A's asset inventory.
      • See detailed documentation: Scanner Mobility & Lifecycle.

    Subnet MAC Address Whitelist (Alert Suppression)¶

    To eliminate alert fatigue in dynamic environments or for recurrent legitimate devices (e.g., printers, IoT, test benches), RTMS supports per-subnet MAC whitelisting:

    • Dedicated Table (admin.subnet_mac_whitelist):
    • id: Primary key.
    • subnet_cidr: Target CIDR block (e.g., 192.168.1.0/24).
    • mac_address: Normalized MAC address (XX:XX:XX:XX:XX:XX).
    • label: Whitelisting rationale or device label.
    • created_by / created_at: Audit attribution for authorizing administrators.

    • Unique constraint on (subnet_cidr, mac_address).

    • Scan Engine Enforcement (rtms-scanner/main_scanner.py):

    • On every scan cycle, the whitelist is dynamically loaded via rtms_commons.db_client.load_subnet_mac_whitelist().
    • When a host is discovered on a target subnet (ctx_target), its MAC address is checked against the whitelist for that CIDR block.
    • If the MAC address is whitelisted:
      • NEW_HOST alerts (and unknown device / missing hostname warnings) are automatically suppressed.
      • The device is registered in global_known_macs with the fallback label "Whitelisted-Device" if reverse DNS resolution has not completed yet.
      • An explicit log notice is recorded: [MAC WHITELIST] Host <IP> (MAC: <MAC>) is whitelisted on subnet <SUBNET>. Suppressing unknown device and missing hostname alerts.
